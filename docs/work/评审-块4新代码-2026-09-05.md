# 评审 · 块4新增代码大规模审查（v0.2.12→v0.2.13 三批）

> 背景：4.3 开工前防错误堆积（作者 2026-09-05 发起，范围作者定=新代码深审+横切，存量只核对已登记弱点）。
> 审查对象：domain 五新件（envelope/proposal/ledger-index/promise-prefilter/inbox）+ server/ledger 挂线、core scan、壳收件箱三件、bench 三件，约 2200 行产码 + 1100 行测试。

## 方法与证据等级

- 六路只读子代理并行深审（domain / core+契约 / shell+安全 / scripts+文档一致性 / 规范自上而下 / 测试面），结论均带 file:line。
- 主代理承重断言亲证：全部 P1 候选逐条读码复核；争议点（判据口径）加跑零 LLM 实测探针（`.bench/probe-recheck-scope.mjs`，导生可焚）。
- 基线复核（0905 实跑）：`npm run check` 0 错（check-versions 六处一致 v0.2.13）、`npm test` exit 0 全绿（shell 403 可见，总账 1060 与发版披露一致）。
- 证据标注：【亲证】主代理读码确认；【推演】子代理静态分析未实跑；【待验证】现象+假设不定性。

## 总评

**架构与契约纪律整体过关，但新链路存在一簇会咬人的缺陷。** 过关面：42 工具=38+4 零删改、无运行时循环依赖、账本 CAS/快照未被破坏、壳零 `{@html}`、鉴权/CORS 未动、check-versions/check-docs 实跑过。缺陷面集中在三处：①壳扫描链路真实条件下必挂且静默（P1-1）；②收件箱机器态的写闸/回读验证/状态机/重入语义缺口（P2 簇，多数潜伏于「scan 只产 promise 维」的现状）；③评测脚本判据口径（已实测，在册决策幸存）。1060 测试全绿掩盖的是边角与对抗输入——测试缺口矩阵见下。

## P1（2 条，均【亲证】）

### P1-1 壳扫描链路 30s 死线 + 全链静默失败：4.2 扫描在真实条件下不可用，且服务端继续烧 LLM

- 证据：`shell/src/lib/core.ts:16`（DEFAULT_REQUEST_TIMEOUT_MS=30_000）、`:242`（缺省吃它）、`scanPromise`（core.ts:345-351）不收 opts——对照 `review.svelte.ts:314` 长任务显式传 600s 的既有口径；服务端 `core/src/scan.ts:141-166` 逐章串行 LLM（缺省 20 章，每章一次 generateText，总时长远超 30s）。
- 链路：壳 30s abort → `scan.ts:123` res.on('close') 触发 abort → 尾部 inbox_append（`:173`，携带已中止 signal）失败 → 整批提案丢弃；而进行中的 generateText 用服务端自有 `timeoutSignal`（`:144,155`），客户端断连后**继续烧完后续章的 LLM 调用**（对照 review.ts:110 用 AbortSignal.any）。壳侧 `inbox.svelte.ts:101-111` scan/decide 均 try/finally 无 catch + `InboxList.svelte:23` `void inbox.scan()` → unhandled rejection，UI 零反馈（按钮闪回「扫描」）。
- 影响：承诺伏笔窄域全环（4.2 旗舰交付）在真实数据规模上不可用；成本静默泄漏；用户无从得知失败。
- 修复方向：scanPromise 加 opts 并传长超时（对齐 review 600s 口径）；服务端 `AbortSignal.any([abort.signal, timeoutSignal])`；壳 scan/decide 失败写 `work.error`（对齐 candidates 模式）。半天内可修。

### P1-2 protect 写闸对 remove 全维失明：受保护条目可经 DELETE 提案删除，拦档语义失效

- 证据：`domain/src/proposal.ts:78-94`——protectHit 只从 `op.entry.{name,character,id}`、`op.item`、`op.name` 收集比对串；remove op 形如 `{op:'remove', dimension, id}` 三者皆无 → hay 空 → 恒不命中 → validateProposal 放行 → `inbox.ts:192` upsertLedger 落账删除。
- 真实触发链：`core/src/scan.ts:98-107` 对 retire 承诺产 DELETE 草稿——作者登记 protect 的承诺，扫描撤线提案照样可删（缓解：仍需作者点采纳，且账本写有快照可恢复）。
- 影响：违反 reference/05 三档处置「拦=写闸 deny」的核心语义（架构正确性）。
- 修复方向：protectHit 补收 remove 变体的 `id/character/name` 顶层字段。

> 同时承接两条作者口头强调的诉求——多模型矩阵、composer 档位不足。本稿在登记框架上做了三处主动优化

## 前置事实（代码实证，2026-08-24 探查）

- 方案机制（0010）：`.novel/schemes/*.md` frontmatter = 通道→角色映射（chat/rewrite/review），**壳侧解析**成 persona 名随请求带出，core 只懂 persona 不懂方案；方案 pill 在 Toolbar 恒可见，切换即生效（无请求）。
- 预设与三槽：预设来自 config.json（Tauri 转 `LLM_PRESET_<ID>_*` env 注入）+ 环境变量；`LLM_ASSIGN_(WRITING|BACKGROUND|REVIEW)` 三用途槽；**未分配回落「第一预设」= env 扫描序第一个**（config.ts:123-129，脆弱兜底）。
- 档位现状：composer 两档 pill 互切（chat 请求体 tier: writing|background）；rewrite 同枚举两档；review 固定 review 槽；continue/摘要/质检固定 background 槽；审阅面板 quick/standard/deep 是壳侧级别非模型档。
- 碰撞现状：单次 chat 请求、**单模型**按协议输出四节（方案/漏洞/反方/裁决），无三方编排；**mode/tier 均不落库——「开舱率低则从简」的决策依据目前不存在**。
- 设置面板已能编辑预设增删改与三槽指向，并显示「当前生效」三槽；无任何方案↔模型 UI。

## 决策

### 1. 绑定粒度：按用途槽（writing/background/review），不按「通道×角色」

scheme frontmatter 加可选嵌套 `model:` 块，键 = 用途槽名：

```yaml
---
kind: scheme
name: 体验优先型
chat: 小白读者
review: 小白读者
model:
  writing: GPT_LUNA        # chat/rewrite 的贵档（写作档）
  background: OX_ALPHA_FREE  # chat/rewrite 的便宜档（背景档）
  review: DEEPSEEK_PRO     # 审阅冷读
---
```

- **为什么降维**：三个普通通道（chat/rewrite/review）按设计就是单角色——非结构化输出里混合多副姿态会被模型平均成稀糊，单声音是生成质量要求（见下方对 0010 的修订注）。通道单角色之下，「通道×角色」矩阵每列单值，纯过度设计；按用途槽则与设置面板三槽、`/v1/llm` effective 三槽同一语义轴，作者心智零新增。
- **对 0010 的一处措辞修订**（旧件不改写，修订关系记于此）：0010「不做多人格叠加进单通道」收窄为三层——①**单次生成单声音**（质量规则，长期有效）；②**通道内多角色必须走结构化编排**（分节/分轮次，每节一个声音、一个模型位；碰撞协议四节已是先例，真三方会审是其深化，0014 既定方向本就需要多角色进通道，原措辞会挡自己的路）；③**普通通道默认单角色**。本稿按③对普通通道做槽级绑定；碰撞通道的多角色×多模型绑定归 3c（数据后立项），届时方案加 collide 三方子键即名正言顺的加法。
- **只覆盖显式写出的键**，缺省回落对应用途槽（再回落第一预设）——加法兼容，旧方案无 model 块零变化。
- **覆盖面 = 方案三通道**（chat/rewrite/review，与 0010 通道面一致）；continue/摘要/质检等固定档通道**不随方案**（见被否选项 4）。
- chat 与 rewrite 共用 writing/background 两键（同枚举）；若真实使用出现「对话便宜、改写贵」的分绑诉求，升级为通道×档位子键（如 `chat-writing:`），加法路径已留。

### 2. 解析分工：壳解析、core 收字段（persona 同构，0010 边界不动）

- 壳：激活方案的 model 块按请求档位解析出预设 id，随请求带出——chat/rewrite/review 三端点请求体各加可选 `model` 字段（预设 id 字符串）。
- core：请求级 model > 该请求档位的用途槽 > 第一预设；**请求 model 指向不存在的预设 → 400 中文报错**（不静默回落——与「配置缺失启动即抛错」同纪律）。
- core 依然不懂方案，只新增一个请求级覆盖字段；e2e/promptfoo 不传该字段，行为面不变。

### 3. 校验与可见性（防「静默换模型」）

- `/v1/posture` 返回各方案的 model 绑定及 valid 标记（预设 id 在 `/v1/llm` 预设池内 = valid）。
- 激活含未知预设 id 的方案：**允许激活但弹显式警告**（「方案绑定的模型 X 不在预设池，该槽将回落用途槽」）——预设后来被删同理，pill 上红点 + title 显示回落结果，不静默。
- 方案 pill：下拉项与 title 附模型阵容摘要（如「体验优先型 · 写作 GPT_LUNA / 审阅 DEEPSEEK_PRO」）；未绑定显示「模型：随全局」。
- 设置面板「模型预设」组尾部加**只读**展示：当前激活方案的 model 绑定与最终解析三槽（编辑仍走改 md 文件——壳内编辑 UI 维持 0010 缓做）。

### 4. 档位两轴论：R2「多档位」诉求由方案轴承接，不扩档位枚举

- **档位（writing/background）= 成本开关**，语义保持二值贵/便宜；**方案 = 模型阵容**，切方案整套换（角色+模型）。两轴正交：方案 pill 换阵容，composer pill 换成本档。
- 作者「要多档位」的真实诉求是多模型可切换——由方案轴满足（Toolbar pill 恒可见，0010 已定），不再往 tier 枚举里加第三档（档位语义稀释，且 core/chat/rewrite/continue 四处枚举联动，收益低）。

### 5. 数据前置（批 3a，先行独立发）：mode/tier 落账，碰撞深化的依据从无到有

- stats 日账（stats-store，与码字日历同库同节奏）加四个计数：`chatTotal` / `chatCollide` / `chatWriting` / `chatBackground`；core chat 处理器请求起步处 fire-and-forget upsert。
- 开舱率 = chatCollide/chatTotal，档位使用率 = chatWriting/chatTotal，均可按日回看——「开舱率低则从简」从此有据；同时服务北极星仪表（真实使用分布）。

### 6. 碰撞深化：块 3 不做编排，等 3a 数据另立项

- 单模型四节自碰撞维持现状；模型绑定落地后「讨论陪练」姿态已可随方案换模型（同模型自碰撞=同上下文假三方，0014 已定性）。
- **真三方会审**（漏洞/反方节由第二模型产出，core 需把单请求拆成多次模型调用的编排）体量大，等开舱率数据：开舱可观（占比持续 >某阈值，具体由数据说话）则另立决策件立项；低则长期从简。

### 7. 断言策略（块 2 前置纪律延续：改行为先有断言网）

- core 单测覆盖解析序全表：请求级 > 槽 > 第一预设 > legacy 四级，及 400 防呆、posture valid 标记。
- shell store 单测：方案 model 块 → 三通道请求体 model 字段的挂载与缺席、未知预设的警告路径。
- promptfoo 不加用例：模型路由层在 provider 聚合里不可见，行为面（工具调用纪律）本批不变；强凑断言是假安全。

## 前端触点与排布约束（集中清单，防实施漂移）

**动四件——全是既有控件的内容增量，零按钮挪位、零新形态：**

1. **Toolbar 方案 pill**：下拉项附模型阵容摘要（「体验优先型 · 写作 GPT_LUNA」，超长按现有菜单样式截断或副行，实施时定）；title 显示激活方案三槽最终解析结果；绑定失效红点。数据全部来自 /v1/posture 返回值（core 改动驱动），壳零新增解析逻辑，触发链不变（activate 后重拉 posture）。
2. **激活警告**：复用 notice 机制（T12 带 action 放宽 12s 先例）——激活含未知预设的方案时弹「方案绑定的模型 X 不在预设池，该槽将回落用途槽」，允许激活不阻断。
3. **SettingsColumn「模型预设」组尾**：只读块「当前方案的模型绑定」（三槽绑定值+最终解析+失效标记）；不新增交互，编辑仍走改 md 文件（壳内编辑 UI 维持 0010 缓做）。
4. **（批 3a）码字日历格子 tooltip 加一行**「对话 N · 碰撞 M · 写作档 K」——开舱率/档位率的日常可见面，仪表化落点（0014「报数不报感」）；无面板新立项。

**显式不动三件：**

5. composer 档位 pill 两档互切不动（决策 4 两轴正交——档位=成本开关，方案=模型阵容）。
6. 碰撞胶囊不动（多角色×多模型的编排归 3c，届时另议触点）。
7. 其余按钮/栏位/面板排布零变化。

**发送链（store 层，非 UI）**：chat.svelte.ts / candidates 链（rewrite）/ review.svelte.ts 三处发送体挂可选 model 字段——按请求档位取激活方案 model 块对应键，缺席不带；与 persona 字段的挂载点同构。

## 被否选项

1. **「通道×角色」绑定粒度（0014 原登记案）**：普通通道单角色（见修订注③，非结构化输出的单声音质量要求），矩阵退化为列向量，表达力与按槽等价、键面与心智成本翻倍——否。碰撞通道的角色×模型绑定不在此列（归 3c）。
2. **通道×档位粒度（chat-writing 与 rewrite-writing 分绑）**：无已登记诉求，键面 5+；留作真实诉求出现后的加法子键——本稿不做。
3. **core 读 active-scheme 自行解析模型**：破「core 只懂 persona 不懂方案」边界（0010 第 4 条），且 core 需感知书目录方案热重载——否。
4. **方案覆盖 continue/摘要/质检等固定档通道**：方案的通道面就是 chat/rewrite/review（0010），扩到后台通道会让「触发式续写」与主笔模型分裂、账单不可预期——维持固定档。
5. **扩 chat tier 枚举做真三档**：档位=成本开关语义被稀释，四处枚举联动——R2 诉求由方案轴承接（决策 4）。
6. **未知预设静默回落**：违「配置缺失显式暴露」纪律，预设增删会静默换模型——改为激活警告+红点+400 防呆三层。
7. **碰撞多模型编排进块 3**：体量大且缺开舱率数据——3a 先行，数据后立项。

## 置信度与重审触发

- 置信度：**高**——无新机制，全部复用既有语义轴（三槽）、既有分工（壳解析/core 收字段）、既有纪律（显式报错/加法兼容）。
- 重审触发：①作者真实使用要求 chat 与 rewrite 同档分绑 → 升级通道×档位子键；②3a 数据显示碰撞开舱可观 → 真三方会审另立决策，届时方案加 collide 三方绑定（角色×模型子键，修订注②的落点）；③预设池规模大到三槽+方案两层不够管（如按卷切阵容） → 重审绑定层级。
